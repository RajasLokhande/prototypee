# PROJECT
AI-Assisted IDOR/BOLA Repair System for a Document Portal

# PROBLEM STATEMENT

Build an AI-assisted system that tracks down an access flaw in a document portal and fixes it safely:

**Proof first → smallest fix → verify nothing else broke.**

The document portal is a web application where users upload, store, list, open, and download documents.

The portal intentionally contains an **IDOR / BOLA (Broken Object Level Authorization)** vulnerability where an authenticated user can access another user's document by changing the document ID in the API request.

The prototype must automatically:

1. Detect the suspected authorization flaw.
2. Produce concrete proof that the flaw exists.
3. Analyze the relevant source code using AI.
4. Generate the smallest possible code patch.
5. Apply the patch only inside a safe sandbox/workspace.
6. Run security tests and functional regression tests.
7. Show whether the repair succeeded without breaking legitimate functionality.
8. Present the complete process in a simple web dashboard.

IMPORTANT:
This is a LOCAL DEMONSTRATION ONLY.
Do not scan, attack, or interact with real websites or third-party systems.
The intentionally vulnerable document portal must run locally.

Create two users:

Create documents such as:

The vulnerable endpoint should look conceptually like:

GET /api/documents/:id

The vulnerable implementation should:
- authenticate the user
- retrieve the requested document
- return it

BUT it must initially fail to verify whether the authenticated user is authorized to access that document.

Example:

Alice is authenticated.

Alice requests:

GET /api/documents/201

Document 201 belongs to Bob.

The vulnerable application incorrectly returns:

200 OK

This is the vulnerability.

After repair, the same request must return:

403 Forbidden

while legitimate access must continue working.

4. AI ANALYZER
   Give the AI:
   - vulnerability evidence
   - proof record
   - relevant source code
   - application authorization rules
   - patch constraints

The AI should determine:
   - root cause
   - affected file/function
   - why authorization is missing
   - safest minimal repair

5. PATCH GENERATOR
   The AI must generate a MINIMAL PATCH / DIFF.

Do not rewrite the entire project.

Prefer output like:

- added authorization check
- no unnecessary refactoring
- no database schema changes unless absolutely necessary

   - lines added
   - lines removed
   - diff

6. SAFE PATCH SANDBOX
   Never directly modify the original vulnerable source during analysis.

Instead:
   - create a temporary/sandbox copy
   - apply the patch there
   - run tests there

Only mark the patch as accepted if verification succeeds.

7. VERIFICATION ENGINE

Run at least:

REGRESSION / FUNCTIONAL TESTS
F. User login works
G. Document listing works
H. Document upload works
I. Owner can open/download own document
J. Document deletion still works if implemented

# SECURITY SCANNER DETAILS

Implement a local scanner module.

It should be able to:

1. Authenticate as Alice.
2. Obtain Alice's document list.
3. Identify candidate document IDs.
4. Attempt access to another user's document.
5. Compare:
   requester user ID
   document owner ID
   HTTP response
6. Confirm BOLA/IDOR when:
   requester != owner
   AND
   server returns unauthorized success.

Do not claim a vulnerability solely because a request returns 200.
Use ownership information and controlled proof evidence.

Structure the scanner output as JSON.

Example:

{
  "vulnerability": "BOLA",
  "confirmed": true,
  "requester": {
    "id": 1,
    "name": "Alice"
  },
  "targetDocument": {
    "id": 201,
    "ownerId": 2
  },
  "expectedStatus": 403,
  "actualStatus": 200,
  "endpoint": "/api/documents/201",
  "evidence": "CANARY_DOCUMENT_201"
}
